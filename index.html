DevSecOps Culture & Principles

DevSecOps integrates security practices within the DevOps process, making security a shared responsibility throughout the software development lifecycle.

🤝 Collaboration & Shared Responsibility

Breaking down silos between Development, Security, and Operations teams. Everyone is responsible for security.

⚡ Shift Left

Integrate security early in the development process, not as an afterthought. Catch vulnerabilities before production.

🤖 Automation First

Automate security testing, compliance checks, and deployment processes to ensure consistency and speed.

📊 Continuous Monitoring & Feedback

Monitor applications and infrastructure continuously, providing rapid feedback to teams.

Core DevSecOps Principles

Key Pillars

  • Security as Code: Treat security policies and configurations as code, version controlled and automated
  • Continuous Security: Integrate security checks at every stage of the pipeline
  • Fast Feedback Loops: Provide immediate feedback on security issues to developers
  • Infrastructure as Code (IaC): Manage infrastructure through code for consistency and auditability
  • Immutable Infrastructure: Replace rather than update servers to ensure consistency
  • Least Privilege: Grant minimum necessary permissions to users and systems
Remember: Security is not a gate at the end of development—it's woven into every step of the process.

CI/CD Concepts

Continuous Integration (CI)

Developers frequently merge code changes into a central repository, where automated builds and tests run.

  • Frequent code commits (multiple times per day)
  • Automated build process
  • Automated testing (unit, integration, security)
  • Fast feedback to developers

Continuous Delivery/Deployment (CD)

Automatically deploy all code changes to testing or production environments after the build stage.

  • Continuous Delivery: Code is ready to be deployed at any time (manual approval)
  • Continuous Deployment: Every change automatically deployed to production

GitHub Actions Basics

GitHub Actions is a CI/CD platform that allows you to automate your build, test, and deployment pipeline directly in GitHub.

Core Concepts

  • Workflow: Automated process defined in YAML file (.github/workflows/)
  • Event: Triggers that start a workflow (push, pull_request, schedule, etc.)
  • Job: Set of steps that execute on the same runner
  • Step: Individual task that runs commands or actions
  • Action: Reusable unit of code (from marketplace or custom)
  • Runner: Server that runs workflows (GitHub-hosted or self-hosted)
Workflow File Location: .github/workflows/your-workflow.yml

GitHub Actions Workflow Structure

name: CI Pipeline

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    
    steps:
    - name: Checkout code
      uses: actions/checkout@v3
      
    - name: Set up JDK
      uses: actions/setup-java@v3
      with:
        java-version: '17'
        distribution: 'temurin'
        
    - name: Build with Maven
      run: mvn clean install
      
    - name: Run tests
      run: mvn test
Pro Tip: You can run multiple jobs in parallel or create dependencies between jobs using the needs keyword.

Build & Test Pipelines

Typical Java Build Pipeline Stages

  1. Checkout: Pull the latest code from repository
  2. Setup Environment: Install JDK, Maven/Gradle, dependencies
  3. Compile: Compile source code
  4. Unit Tests: Run fast, isolated unit tests
  5. Integration Tests: Test component interactions
  6. Code Coverage: Measure test coverage
  7. Static Analysis: Check code quality (SonarQube, Checkstyle)
  8. Security Scanning: Scan for vulnerabilities (OWASP Dependency Check)
  9. Build Artifact: Create JAR/WAR file
  10. Upload Artifact: Store build artifact for deployment
Best Practice: Fail fast! Run faster tests first to get quick feedback.

Pipeline Failures & Troubleshooting

Common Pipeline Failures

Build Failures

Compilation errors, missing dependencies, syntax errors

Test Failures

Unit test failures, integration test issues, flaky tests

Environment Issues

Wrong Java version, missing tools, configuration errors

Timeout Errors

Long-running tests, network issues, resource constraints

Troubleshooting Steps

  • Check the pipeline logs for error messages
  • Reproduce the issue locally
  • Verify environment configuration (Java version, dependencies)
  • Check for recent code changes that might have caused the failure
  • Review test output and stack traces
  • Use debug logging for more details

Debugging GitHub Actions

Useful Debugging Techniques

1. Enable Debug Logging

Set repository secrets: ACTIONS_STEP_DEBUG and ACTIONS_RUNNER_DEBUG to true

2. Use the Run Command with Output

- name: Debug info
  run: |
    echo "Java version: $(java -version)"
    echo "Maven version: $(mvn -version)"
    ls -la

3. Review Artifacts

Upload logs and test reports as artifacts to review after the pipeline completes

- uses: actions/upload-artifact@v3
  with:
    name: test-results
    path: target/surefire-reports/

Sample Java CI Workflow

name: Java CI with Maven

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
    - name: Checkout repository
      uses: actions/checkout@v3

    - name: Set up JDK 17
      uses: actions/setup-java@v3
      with:
        java-version: '17'
        distribution: 'temurin'
        cache: maven

    - name: Build with Maven
      run: mvn -B package --file pom.xml

    - name: Run tests
      run: mvn test

    - name: Generate test report
      if: always()
      uses: actions/upload-artifact@v3
      with:
        name: test-results
        path: target/surefire-reports/

Introducing & Fixing Failures

Step 1: Introduce a Failing Test

Change the test assertion to make it fail:

@Test
public void testAdd() {
    Calculator calc = new Calculator();
    assertEquals(10, calc.add(2, 3)); // This will fail!
}

Step 2: Commit and Observe

Commit this change and watch your GitHub Actions pipeline fail. Check the logs to see the error message.

Step 3: Fix the Test

Revert the test to the correct assertion:

@Test
public void testAdd() {
    Calculator calc = new Calculator();
    assertEquals(5, calc.add(2, 3)); // Fixed!
}

Step 4: Verify

Commit the fix and watch the pipeline turn green again!

CI/CD Best Practices

  • Keep builds fast: Optimize for speed (use caching, parallel jobs)
  • Make builds deterministic: Same input should always produce same output
  • Fail fast: Run quick checks first, expensive ones later
  • Maintain clean build logs: Clear, actionable error messages
  • Use branch protection: Require passing builds before merging
  • Version control everything: Infrastructure, configuration, and code
  • Monitor pipeline performance: Track build times and failure rates
  • Secure your secrets: Use GitHub Secrets for sensitive data
  • Regular maintenance: Update dependencies and actions regularly
Golden Rule: If it hurts, do it more often. Frequent small changes are easier than big bang releases.
